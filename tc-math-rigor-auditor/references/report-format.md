# 嚴謹性審查報告格式

預設檔名為 `rigor_reviews/rigor_TC_<來源檔名主體>.vN.md`（例如審查 `ch02.ipynb` 得到 `rigor_TC_ch02.v1.md`；`sc-math-rigor-auditor` 依這個名字找 TC 報告），N 取既有最高版本加 1。未指定落盤且僅問單句時，可直接在對話中提供同等證據，不必建立報告檔。

## 報告開頭

記錄：

- 審查日期、目標檔案、來源 commit（無 git 時說明）、工作區修改狀態、來源檔完整 SHA-256。
- 審查語言、涵蓋章節及 cell 範圍；已閱讀的前置定義、相關章節與明確未查範圍。
- 主審與覆核方式；只有實際可知的模型名稱才填寫，不臆測版本。
- 驗證工具與實際執行狀態；獨立覆核狀態：未做／完成／部分完成。

## 範圍覆蓋表

| 小節或完整論證 | cell／label | 檢查結果 | 限制 |
|---|---|---|---|

結果使用「已審，有發現」「已審，未發現問題」「部分已審」「未審」。沒有發現不是形式化證明的正確性保證；不提供沒有依據的正確率。

## 發現清單

依影響排序，每筆使用穩定 id（例如 `rigor-chap1-001`）。同一根因的多處出現合併列位置，避免重複計數。重審沿用已有 id，新問題追加 id。

每筆包含：

1. **類型／影響／判斷**：使用 SKILL.md 的獨立分類。
2. **定位**：檔案、§章節、0-based cell index、cell id（若有）、label（若有）、1-based cell 內行號；不存在的欄位寫「無」，不可杜撰。
3. **原文**：精確節錄足以判斷的文字，保留公式及必要前後文。
4. **已考慮的上下文**：哪些既有假設或前文定義適用，為何仍構成問題。
5. **證據**：推導、有效反例、可重現的驗證片段及實際結果，或來源連結與具體支持的命題。
6. **最小修改建議**：給可直接定位的建議文字，說明補條件、縮小結論或改證明何者適合；保留作者教學意圖。
7. **影響與覆核**：受影響例題、後續章節及現有譯文；只列實際查到者。記錄覆核支持、否定或尚有分歧及理由。
8. **處理狀態**：`open`／`accepted`／`fixed`／`dismissed`，與 `confirmed` 等判斷分開。只有實際修改且驗證後才能寫 `fixed`。

純風格建議獨立放在文末選用區，不列入數學錯誤統計。待驗證問題獨立列出，指出需要什麼證據才能定案。計數從最終條目及其欄位計算，不能以文字搜尋命中註解的次數計數。

## 結尾

列出最重要的修訂順序、未解分歧與尚未驗證範圍。沒有高影響問題時如實陳述，不為湊報告製造問題。未授權修改教材時，建議文字仍只是提案。
